Agent-2：Tool Calling —— LLM 怎么「准确」调函数

对应代码：codesage.py / assetsage.py 的 TOOLS_DOC、_exec_tool；llm.py 的 chat_json
LLM 不会真的「调用」函数，它只会输出一段 JSON；真正执行函数的是你的 Python 代码。

1. 整条链路（先看图）

图 1：一次 Tool Calling = 说明书 → JSON 决策 → 解析 → 白名单派发 → 结果回灌

2. 四个关键点

① 说明书（TOOLS_DOC）决定 LLM 会不会用对

说明书写在 system prompt 里。每个工具必须写清：用途 / 参数名 / 返回结构 / 易错点。

2. get_asset_info
   参数: {"asset_path": "/Game/xxx/SM_Foo.SM_Foo"}
   **重要**: 必须是 ObjectPath，末尾要重复资产名     ← 把踩过的坑直接写进说明书

② 输出格式：固定一个 JSON 形状

{"thought": "这步想拿什么证据", "tool": "工具名", "args": {...}}
手段代码位置作用
"format": "json"llm._post_ollama让 Ollama 强制输出 JSON
temperature = 0chat_json决策要稳定，不要发散
num_ctx = 8192_post_ollama默认 2K 会被工具输出撑爆

③ 解析：宽进严出

宽进：LLM 输出带了废话、代码块或前缀，也尽量容忍。严出：交给后面的必须是合法 dict，否则返回 {"error": ...}。

图 2：chat_json 是外层，里面的 for 循环负责重试；_extract_json 只是被它调用的「解析一次」小函数
常见疑问：_extract_json 里没调用 chat_json，重试从哪来？
调用方向是反的：chat_json 调用 _extract_json（llm.py 第 89 行），不是反过来。
_extract_json 只负责「解析一次」：成功返回 dict，失败返回 None，它不知道重试的存在。
重试逻辑在 chat_json 自己的 for attempt in range(retries + 1) 里。retries=1，所以最多请求 LLM 两次。

四步走

  1. json.loads 直接解析：成功就直接返回，大多数情况到这里结束。
  2. 截取首 { 到末 } 再解析：专治 LLM 多说话或带 ```json 前缀。以上两步都在 _extract_json 里。
  3. 仍失败 → 追加提示重试：chat_json 把坏输出和「请重新输出纯 JSON」加进对话，再请求一次。
  4. 重试也失败：返回 {"error": ..., "raw": ...}，Agent 层走 _fallback_summary 收尾。

例子：LLM 输出带了前缀。

好的，我来查一下：{"tool":"lookup_symbol","args":{"name":"Foo"}} 希望有帮助

第 1 步整段解析失败；第 2 步切出 {...} 解析成功，拿到工具调用，不需要重试。

核心代码（shared/llm.py）：

# 内层：只解析一次，不重试
def _extract_json(text):
    try:    return json.loads(text)              # 第 1 步
    except json.JSONDecodeError: pass
    start, end = text.find("{"), text.rfind("}")
    if start >= 0 and end > start:               # 第 2 步
        try:    return json.loads(text[start:end+1])
        except Exception: return None
    return None

# 外层：重试循环在这里
def chat_json(system, user, retries=1, ...):
    for attempt in range(retries + 1):
        content = _post_ollama(messages, ...)
        parsed = _extract_json(content)          # ← 调用内层
        if isinstance(parsed, dict):
            return parsed
        if attempt < retries:                    # 第 3 步：追加提示再来一轮
            messages += [{"role": "assistant", "content": content},
                         {"role": "user", "content": "请严格重新输出纯 JSON"}]
    return {"error": "invalid json", ...}        # 第 4 步
为什么要这样拆：解析是纯函数，容易单独测试；重试涉及网络和对话历史，放在外层。两件事各管一段。目标模型是 7B 小模型，偶尔多说话或漏括号，没有这层兜底，一次坏输出就会中断整个 Agent。

读懂 chat_json 里的变量：哪些固定，哪些自起

名字固定格式吗说明
messages 的结构固定（Ollama / OpenAI 通用）列表，每项是 {"role":..., "content":...}
role 的取值固定system / user / assistant
content 这个键固定消息正文的字段名
messages 这个变量名自己起的叫 msgs 也行
last_content / last_error / parsed自己起的纯局部变量，和协议无关

① messages：发给 LLM 的整段对话。LLM 本身没有记忆，每次请求都要把「到目前为止的整段对话」一起发过去，它才知道前面说过什么。

role谁说的本项目里装的是什么
system给 LLM 的规则SYSTEM_PROMPT（含工具说明书）
user用户的话"\n\n".join(history)（任务 + 之前的思考和观察）
assistantLLM 之前的回答重试时放进去的那次坏输出

② content：每条消息的正文，类型是字符串。发出去时是你写的，收回来时是 LLM 生成的。_post_ollama 取的就是返回里的 message.content：

{"message": {"role": "assistant", "content": "{\"tool\":\"lookup_symbol\", ...}"}}
注意：LLM 即使写的是 JSON，在这里也只是一段文字，所以才需要 _extract_json 把它解析成 dict。

③ last_content / last_error：记录最近一次失败的现场。定义在循环外，因为循环结束后还要用。

变量装什么用在哪
last_content最近一次 LLM 返回的原文（坏 JSON）重试时当作 assistant 消息放回对话；最终失败时放进 raw 方便排查
last_error失败原因的短字符串最终失败时放进返回的 error

last_error 三种取值，对应三种失败：

  1. "llm call failed: ..."：网络或服务挂了。
  2. "empty response"：LLM 返回了空文本。
  3. "invalid json"：有内容，但解析不出 dict。

④ parsed：_extract_json 的返回值。只有两种可能：dict（成功）或 None（失败）。代码还多查一次 isinstance(parsed, dict)，因为 LLM 可能输出合法 JSON 但不是对象，比如 [1,2] 或 "hello"，这也算失败。

重试时 messages 怎么变

图 3：重试不是「原样再问一次」，而是把失败现场追加进对话，让 LLM 带着错误重答

对应代码里的 last_content or "(empty)"：上次若是空回复，就放一个占位文字，因为 content 不能为空字符串。

一句话记住：messages 的格式是行业通用的固定格式，背下来即可；last_content、last_error、parsed 都是普通变量，改名完全不影响。

④ 派发：白名单 + 参数矫正

  • 白名单：_TOOL_MAP 里没有的工具名，直接返回「未知工具」，LLM 编不出新命令。
  • 参数矫正：_normalize_args 把 LLM 常写错的参数名自动改对（directory → path、component_class_name → component_class），省掉一轮白跑。
经验：LLM 总会犯同一类错 → 与其反复改 prompt，不如在代码层兜住（矫正、白名单、去重）。

3. 你该记住的 3 件事

  1. Tool Calling = 「说明书 + JSON 约定 + Python 派发」，LLM 只负责选。
  2. 输出必须可解析：format=json + 提取 + 一次重试。
  3. 入口要白名单，常见错误在代码层矫正。
